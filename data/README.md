# Submiq Synthetic Dataset

## Structure

```text
data/
├── raw/
│   ├── generate_synthetic_dataset.py   # reproducible generator (fixed seed)
│   └── submiq_dataset.csv              # primary research dataset (120 rows)
├── processed/
│   ├── make_splits.py                  # deterministic split generator (fixed seed)
│   ├── development.csv                 # 85 rows (~70%) - module development/tuning
│   ├── validation.csv                  # 25 rows (~20%) - validation and weight selection
│   └── test.csv                        # 10 rows (~10%) - held-out evaluation set
└── README.md
```

The synthetic dataset is the research dataset for this project, not an auxiliary or fallback dataset. It therefore lives directly under `raw/`.

The `processed/` directory contains derived deterministic splits of `raw/submiq_dataset.csv`. These files are generated by `make_splits.py` and should not be edited manually.

## Why labels beyond "AI vs human"

A completeness-only or AI-detection-only ground truth would not adequately represent the multidimensional nature of onboarding verification.

The dataset therefore labels each submission across the verification dimensions independently. This allows individual verification modules to be evaluated separately and allows the final scoring and gating process to be evaluated against the expected verdict.

This design supports investigation of whether combining multiple signals provides better verification decisions than relying on a single signal.

## Scenario categories

The dataset contains 120 rows covering both primary behavioral scenarios and edge cases.

### Primary scenarios

| # | Category                  | Rows | Purpose                                                                                       |
| - | ------------------------- | ---: | --------------------------------------------------------------------------------------------- |
| 1 | Complete, genuine (human) |   12 | Baseline positive case                                                                        |
| 2 | Human-written, suspicious |   12 | Tests whether suspicious content can be identified without relying on AI detection            |
| 3 | Poor-quality writing      |   12 | Tests the text-quality module                                                                 |
| 4 | Mixed human/AI-edited     |   12 | Represents a realistic mixed-authorship case                                                  |
| 5 | Contradictory information |   12 | Tests cross-field consistency                                                                 |
| 6 | AI-generated, suspicious  |   12 | Tests suspicious AI-generated submissions                                                     |
| 7 | Incomplete                |   12 | Tests the completeness module                                                                 |
| 8 | AI-generated, plausible   |   12 | Tests the case where AI-generated content should not automatically be treated as poor quality |
| 9 | Implausible claims        |   12 | Tests claim-plausibility assessment                                                           |

### Edge cases

The remaining 12 rows represent individual edge-case scenarios, including:

* Career changer
* Unusually long bio
* Very short but genuine submission
* Numeric/keyword-only skills
* Single-sentence genuine submission
* Minimal skills with strong bio
* Skills/role mismatch but plausible submission
* Emoji-heavy formatting
* All-caps formatting
* Overqualified applicant for an entry-level role
* Non-English mixed content
* Resume-paste bullet format

These cases are included to test how the verification modules behave outside the main scenario groups.

Domains represented across the dataset include software engineering (frontend, backend, mobile, embedded, DevOps, data engineering, QA), data and analytics, design, marketing, sales, HR/recruiting, healthcare, legal services, finance/accounting, education, warehouse/logistics, hospitality/retail, customer support/IT helpdesk, real estate, construction, photography, and fitness coaching.

This variety is intended to reduce dependence on a single writing style or industry.

## Dataset columns

* `submission_id` - unique identifier for each submission
* `scenario_category` - scenario used to characterize the submission
* `experience_level` - applicant experience level
* `skills` - submitted skills
* `bio` - applicant biography
* `questionnaire_response` - response to the submission questionnaire
* `source` - `Human`, `AI`, or `Mixed`; ground truth for evaluating the AI-detection module
* `completeness_label` - `Yes` / `No`
* `text_quality_label` - `Good` / `Fair` / `Poor`
* `plausibility_label` - `Plausible` / `Implausible`
* `consistency_label` - `Consistent` / `Contradictory`
* `expected_verdict` - `Verified` / `Needs Improvement` / `Flagged`

The `source` field is used as ground truth for evaluating AI-generated content detection and is not intended to be used directly as an input to the final verification scoring pipeline.

## Class balance

Across the 120 rows:

* **48 Flagged (40.0%)**
* **44 Needs Improvement (36.7%)**
* **28 Verified (23.3%)**

The dataset is therefore not perfectly balanced across final verdicts. This is acceptable during development, but class distribution should be considered when interpreting evaluation metrics.

The component labels are also unevenly distributed. In particular, completeness has 108 `Yes` and 12 `No` labels, while consistency has 108 `Consistent` and 12 `Contradictory` labels. These distributions should be considered when evaluating individual modules because accuracy alone may be misleading for highly imbalanced labels.

## Extending the dataset

Add new rows to the `EXAMPLES` list in `generate_synthetic_dataset.py` rather than editing the generated CSV directly.

After modifying the generator:

1. Run `generate_synthetic_dataset.py`.
2. Run `make_splits.py`.
3. Inspect the resulting dataset.
4. Commit the generator and derived dataset changes together where appropriate.

Keep the random seed fixed when reproducibility is required.

## Before final evaluation

The 120 rows and their labels currently represent a synthetic research dataset and should not yet be treated as independently validated ground truth.

Before reporting final evaluation results, the methodology should include independent review of the labels by at least two reviewers, particularly for borderline `Needs Improvement` cases.

Inter-rater agreement should be measured using Cohen's Kappa where applicable. Any disagreements should be reviewed and resolved according to the project's defined annotation procedure.

The final evaluation should be performed only after the ground-truth labeling process has been documented and validated.
